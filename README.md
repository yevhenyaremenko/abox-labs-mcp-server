# abox-labs-mcp-server

> **Learning project** — built as part of the [abox-labs](https://github.com/yevhenyaremenko/abox-labs) AI Reliability Engineering course (Lab 3).

A Python MCP server built with [FastMCP](https://github.com/jlowin/fastmcp) that exposes Kubernetes operations as tools, with **MCP Elicitation** support for resolving ambiguous requests interactively.

## Could existing tools be used instead?

For the Kubernetes operations themselves — yes:

| Existing option | What it provides |
|---|---|
| [kmcp](https://www.solo.io/blog/introducing-kmcp) (Solo.io) | K8s operations via MCP, deployed as a Kubernetes controller |
| `kagent-tool-server` (bundled with [kagent](https://kagent.dev)) | `k8s_get_resources`, `k8s_get_pod_logs`, `k8s_describe_resource`, `k8s_execute_command` and more — already running in the abox cluster |

**The differentiator here is MCP Elicitation.** Neither kmcp nor kagent-tool-server implement it. When a user says "list pods" without specifying a namespace, existing tools either fail or require the agent to guess. This server instead queries the live cluster for options and asks the user to pick one before executing — using the [MCP Elicitation](https://spec.modelcontextprotocol.io/specification/client/elicitation/) protocol.

## What is MCP Elicitation?

Elicitation is a mechanism in the MCP spec that allows a **server to request additional input from the user** mid-tool-call. Instead of failing on missing parameters, the server sends an `elicitation/create` message to the client with a JSON Schema form. The client renders it, the user fills it in, and execution continues.

```
agent: "get pod logs"
                         ↓ namespace missing
server ──elicit──► client: "Select namespace?" [kagent, mcp, default, ...]
user selects "kagent"
                         ↓ pod_name missing
server ──elicit──► client: "Select pod?" [kagent-controller-xxx, kagent-ui-xxx, ...]
user selects pod
server ──────────► returns logs
```

## Tools

| Tool | Parameters | Elicits when missing |
|---|---|---|
| `list_pods` | `namespace` | namespace (from live cluster) |
| `get_pod_logs` | `namespace`, `pod_name`, `tail_lines` | namespace, then pod name |
| `scale_deployment` | `namespace`, `deployment`, `replicas` | namespace, deployment name, replica count |

## Project structure

```
src/
├── tools/
│   ├── pods.py          # list_pods, get_pod_logs
│   ├── deployments.py   # scale_deployment
│   └── echo.py          # example tool (from scaffold)
├── core/
│   ├── server.py        # dynamic tool loader
│   └── utils.py         # config helpers
├── k8s_client.py        # kubernetes client (in-cluster + local fallback)
└── main.py              # entry point
kmcp.yaml                # server config (generated by kmcp scaffold)
```

## Local development

```bash
uv sync

# stdio mode (default MCP transport)
uv run python src/main.py

# HTTP mode on port 3000
uv run python src/main.py --transport http --host localhost --port 3000
```

For out-of-cluster use, the server falls back to your local kubeconfig (`~/.kube/config`).

## Inspect with MCP Inspector

```bash
# Against the local HTTP server
npx @modelcontextprotocol/inspector@0.21.1 http://localhost:3000/mcp
```

## Deployment (abox cluster)

The server is deployed via [abox-labs](https://github.com/yevhenyaremenko/abox-labs) GitOps:

- **Deployment + Service**: `releases/elicitation-mcp.yaml` — runs the container in HTTP mode with a K8s ServiceAccount scoped to read pods/namespaces/deployments and patch deployment scale
- **RemoteMCPServer**: `releases/elicitation-remote-mcp.yaml` — registers the server with kagent
- **Agent**: `releases/lab3-agent.yaml` — kagent Agent wired to the three tools above
